# Project Purpose

## 为什么创建 Dev Workbench

AI Agent 可以快速完成解释器调试、框架迁移和大型重构，但“任务完成”不等于“使用者理解了过程”。当 Agent 直接交付最终补丁时，使用者经常只能通过结果猜测过程是否正确：

- 看不到规则、函数或任务是如何一步步求值的；
- 不知道某个中间状态为什么出现；
- 很难把文件变化、命令输出和运行效果联系起来；
- 无法在关键决策点暂停、验证、记录自己的理解；
- 一旦最终结果异常，只能重新让 Agent 黑箱排查。

Dev Workbench 的目标不是再做一个“替用户完成任务”的 Agent，而是为 Agent 生成的执行过程提供一个可以亲手操作的理解环境。

核心判断是：

> 自己控制步骤、观察状态变化并留下判断，是形成理解的重要组成部分。Agent 应当铺设体验，而不是拿走这部分体验。

## 产品使命

把复杂的软件执行过程转化为一条可控制、可观察、可回放、可解释和可注释的时间线，让用户以接近亲手完成任务的方式建立理解，同时保留 Agent 带来的效率。

## 目标用户

### 开发者

需要理解解释器、编译器、规则引擎、算法、测试框架或 Agent 内部执行过程。

### 代码审查者

需要审查自己并不熟悉的框架迁移、依赖升级、数据库变更或大型重构。

### 学习者与教师

需要把抽象运行过程变成可以逐步探索、回退、比较和注释的学习材料。

### 使用编码 Agent 的团队

希望保留人工确认、审计记录和中间检查点，而不是只接收最终代码。

## 两个初始工作台

### Execution Explorer

用于理解“系统内部如何执行”：

- 当前执行的规则、函数、表达式或节点；
- 调用栈、目标队列、变量绑定和中间值；
- 分支、失败、回溯与成功路径；
- 任意步骤的跳转、回放、书签和注释；
- 当前状态与前一步状态的差异。

首个参考场景是 Prolog 解释器，但产品模型不能绑定 Prolog。解析器、状态机、工作流、测试运行器和 Agent trace 都应能通过 adapter 接入。

### Migration Center

用于理解和控制“项目如何从状态 A 演进到状态 B”：

- 迁移计划及步骤依赖；
- 每一步实际执行的命令；
- 文件树、代码 diff、测试结果和构建日志；
- 新旧系统并排预览；
- 执行前确认、执行后验收、失败重试和检查点回滚；
- 用户与 Agent 对每一步的解释和注释。

## 产品原则

1. **用户控制时间**：用户决定何时前进、回退、重试或跳转。
2. **状态必须可见**：每一步都要说明输入、动作、输出和变化。
3. **解释绑定证据**：说明必须关联具体事件、文件、命令或运行状态。
4. **生成和执行分离**：Agent 可以生成计划，但执行需要明确确认和安全边界。
5. **历史不可伪造**：已记录事件与快照保持不可变，回放只移动观察游标。
6. **默认可恢复**：高影响步骤应当在 Git checkpoint、worktree 或隔离环境中运行。
7. **Adapter 优先**：共享内核不绑定具体语言、框架或 Agent 服务。
8. **本地优先**：MVP 首先服务本机项目，数据与代码默认不离开机器。

## 非目标

当前阶段不尝试：

- 取代 IDE、Git 客户端或通用终端；
- 自动执行未经用户确认的任意 Agent 命令；
- 保存或展示模型隐藏的内部思维过程；
- 一开始就覆盖所有语言和迁移框架；
- 在没有隔离、身份认证和审计的情况下提供公网多人执行服务。

平台展示的是可记录的执行事件、工具调用、状态快照和面向用户的解释，而不是模型私有推理。

## 成功标准

Dev Workbench 是否成功，不只由“命令是否执行成功”判断，还应衡量：

- 用户能否指出每个关键步骤改变了什么；
- 用户能否从时间线定位首次出现错误的步骤；
- 用户能否在不重新运行全部任务的情况下回看证据；
- 用户能否确认或否决 Agent 的迁移决策；
- 失败后能否恢复到明确检查点；
- 新语言或新工具能否通过 adapter 接入，而不修改共享内核。
